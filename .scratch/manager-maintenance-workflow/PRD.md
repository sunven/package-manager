# 管理器维护工作流

Status: done

## 目标与范围

深化架构审查中的第一个候选：让管理器维护工作流集中拥有确认、执行、扫描互斥与维护后核对，页面与测试通过同一 interface 观察行为。

范围为现有管理器缓存清理、npm/pnpm 全局包卸载及其快照核对。沿用 ADR-0001/0002 的维护范围、清理方案和权限约束；保留扫描队列的去重与并发行为。剪贴板、路径打开、筛选和其他维护领域不在本轮范围内。

## 已确认：第一轮 Q1–Q3

用户于 2026-10-16 回复“按推荐”。

- Q1：延续全局互斥。待确认、执行和核对期间，暂停新的手动刷新与维护；已开始的其他管理器扫描正常结束。
- Q2：命令返回后立即展示执行结果，随后进入“正在核对”阶段。等待包清单、目录占用及适用补充读取结束后恢复操作。
- Q3：执行结果与核对结果分别保存。执行成功而核对失败时，保留已完成事实，单独显示核对失败；“重新读取”只重试核对，不重放维护。

## 重构前的问题

- `src/hooks/usePackageManagers.ts` 通过 `refresh(..., true)` 在维护中启动核对；读取错误进入扫描状态，维护调用者拿不到核对结果。
- 目标管理器处于排队、读取或补充阶段时，不能发起维护；其他管理器已经入队的任务目前仍可启动。
- 缓存清理的 `Failed/NoPlan`、全局包卸载失败及调用异常目前跳过核对。
- 原生缓存结果按步骤区分成功、部分完成、失败和无方案；失败步骤可能已有副作用。全局包卸载也没有统一的“是否已执行”字段。
- 超时或调用回执丢失不能证明维护未执行，重新扫描也不能证明此前命令已经成功结束。
- 现有确认框在执行期间不能关闭。确认目标保存在请求中，但 Homebrew 预演由 App 从当前快照另行取得。

## 已确认：第二轮 Q4–Q6

用户于 2026-10-16 回复“按推荐”，随后要求“继续”实现。

- Q4：原生失败、超时或调用回执丢失后仍尝试核对，保留失败或“执行结果未确认”的事实；不自动重放维护，也不根据新快照反推执行成功。明确未执行的无方案、前置拒绝除外。
- Q5：冻结确认对象与预演。待确认时目标快照更新或目标被停用，使原确认失效，需要重新确认；执行和核对期间禁止停用目标管理器。
- Q6：“重新读取”重新读取目标管理器的完整快照及适用补充信息，只更新核对结果，保留原执行结果，不因此重扫其他管理器。

## 已实现的模块边界

- `src/managerMaintenanceWorkflow.ts` 集中拥有启用列表、快照、扫描队列、补充读取、确认、执行和核对。显式动作通过 `read` / `subscribe` 统一观察，不向调用者开放维护绕过标记。
- `src/managerMaintenanceTauriEffects.ts` 对接现有原生命令与设置存储。测试在同一边界提供可控 effect，不模拟工作流内部步骤。
- `usePackageManagers` 通过 `useSyncExternalStore` 订阅工作流，仅保留选择、筛选、显示汇总、复制和打开路径。StrictMode 的订阅清理不会使工作流失效。
- 继续使用现有两槽扫描队列；单个管理器的任务持有队列资格直到适用补充读取全部结束。刷新失败保留旧快照。
- 确认保存管理器、包名和预演；执行/取消回调绑定操作 ID。执行期间只保存一次结果，随后执行完整核对。核对结束即释放锁，结果保留至关闭或下一次请求。
- 回执等待上限：缓存清理 11 分钟（覆盖现有最长两个 300 秒命令步骤及回执余量），卸载 60 秒（原生命令为 30 秒）。等待超时只意味着结果未确认，不会取消原生任务或推断执行完成；迟到回执不改写已经展示的结果。
- 确认框独立展示执行与核对结果；失败后的“重新读取”只重试目标快照。长预演可以换行、滚动，并通过键盘访问。
