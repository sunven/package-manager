# Codex hooks 管理

Status: done

## 已确认的方向（grill-with-docs，2026-10-14）

- 首版核心用途：查看已经配置的 hooks，包括内容、来源和配置状态，并提供支持的启停操作。
- 创建、编辑、删除配置，以及运行测试、触发记录和失败排查，不纳入本次已选择的首要闭环。
- 管理范围以原生清单为准：hooks 总开关开启时，查看当前 Codex home 的用户配置及已启用插件提供的 hooks。明确提示已禁用插件未展开；总开关关闭时说明原因，不宣称没有配置。此范围以 Q9 为准，收窄了 Q2 中「已安装插件」的初步表述。
- 首版不纳入项目配置，不自行扫描禁用插件或在总开关关闭时重建完整定义清单。
- 页面入口：侧栏「Codex 插件」改为「Codex」，内设「已安装插件／市场源／Hooks」三个页签。
- 信任审查继续使用 Codex 原生界面；本工具展示待信任状态和原因，只启停已经受信任的 hooks，不提供授予信任操作。
- 操作边界：一次只操作单条 hook；总开关关闭或所属插件禁用时说明限制，插件问题引导到「已安装插件」。不连带打开总开关或所属插件，不提供 hooks 总开关操作。
- 目标客户端：同时面向使用同一 Codex home 的本机 CLI 与桌面 App。保存结果只表示配置已保存，提示在新会话中验证，不承诺运行中的会话立即生效。
- 展示内容：列表展示事件、操作摘要、来源／所属插件、启用状态、信任状态及受限原因；详情展开完整命令或 MCP 工具、匹配条件、超时和配置路径。
- 更新方式：首次进入读取、手动刷新及操作后重读，不定时轮询。读取失败时说明原因，已有清单标记过期，不伪装为没有 hooks。
- CLI 依赖：要求本机存在具备所需清单与配置能力的 Codex CLI，包括平常只使用桌面 App 的用户。缺失或不兼容时明确说明，按实际能力判断兼容性，不宣称已知最低支持版本。
- 操作流程：逐条确认事件、操作摘要、来源和目标状态；保存前复核定义、信任和启用状态，发现外部变更时中止旧操作并刷新。保存结果与后续清单读取结果分别报告。

术语以 [CONTEXT.md](../../CONTEXT.md) 中的「Codex 钩子」「Codex 插件」为准。

## 现有背景

- 当前应用已有「Codex 插件」入口及「已安装／市场源」页签，没有专用 hooks 管理能力。
- 既有插件管理限定当前 Codex home 的用户默认配置；本次 hooks 管理沿用当前 home，插件 hooks 的可见范围以原生清单为准。项目配置仍不属于本次范围。见 [ADR-0011](../../docs/adr/0011-codex-plugins-use-cli-inventory-and-user-config.md)。
- 仓库自身的 `.codex/hooks.json` 包含 `PostToolUse` 与 `Stop` 的 command hooks。这只能说明存在项目级配置声明，不能据此断言当前客户端已加载或支持逐项启停。

## 已核实的官方背景

- Codex CLI 的 `/hooks` 支持查看来源、信任、禁用和重新启用单个非托管 hook；桌面 App 也有 hooks 信任审查界面。这些交互能力不等于本工具已经具备稳定的非交互接入协议。
- 用户配置可同时包含 `hooks.json` 与 `config.toml` 中的内联 `[hooks]`；同层双来源合并，跨层也累加。不能自行假定覆盖优先级或把相同内容去重为同一条 hook。
- 信任与启用是不同状态。非托管 hooks 的信任绑定其定义 hash；新定义或变更后的定义需要重新审查，安装或启用插件不自动信任其中的 hooks。托管 hooks 由策略信任，用户不能禁用。
- 插件支持显式声明 hooks 来源；仅在未声明时采用默认文件发现。插件禁用时，其 hooks 不被运行时加载；本机清单的覆盖限制见下文实验结果。
- 全局 `features.hooks` 可关闭 hooks 功能。本次已确认只显示相应限制，不提供总开关操作。
- 当前官方文档没有给出本次能力所需的最低 CLI 版本，也未明确保证 hooks 修改的热加载时机。

依据：[Hooks](https://learn.chatgpt.com/docs/hooks)、[CLI reference](https://developers.openai.com/codex/cli/reference)、[Build plugins](https://developers.openai.com/plugins/build/plugins#bundled-mcp-servers-and-lifecycle-hooks)、[Codex changelog](https://learn.chatgpt.com/docs/changelog)。

## 本机协议核实

- 本机 `codex-cli 0.162.1` 生成的 app-server 协议包含 `hooks/list`，可传入 `cwds`；返回每个工作目录的 hooks、错误与警告。
- 单项元数据包含 `key`、`currentHash`、`enabled`、`trustStatus`、`isManaged`、`source`、`sourcePath` 及可选 `pluginId`。信任状态区分 `managed`、`untrusted`、`trusted`、`modified`。
- 默认和 `--experimental` 协议均包含同样的 hooks 清单结构；但 CLI 帮助仍将 app-server 整体标为 experimental。单版本核实不构成跨版本保证。
- 两份 app-server 协议均无专用 hooks 信任、启用或禁用请求，但有通用配置写接口。后续实际获取的[官方配置 schema](https://learn.chatgpt.com/docs/config-schema.json) 公开了 `hooks.state`：以字符串为 key 的 `HookStateToml` 映射，含可选的 `enabled: boolean` 与 `trusted_hash: string`。不能把“没有专用写接口”解释为“没有公开状态字段”。
- 官方 schema 没有解释 key 或 hash 的生成算法。接入应使用原生清单返回的身份，不自行计算；仅修改目标 `enabled`，保留信任记录。
- `plugin/read` 的 hooks 摘要仅含事件与 key，不足以补全禁用插件中 hook 的内容与状态。
- 隔离临时 home 实验：hooks 总开关开启时，用户 JSON 与 TOML 中的两条 hook 同时返回，并提示同层双来源；总开关关闭时，成功返回空 hooks 清单且没有错误或警告。
- 隔离插件对照：同一份已安装插件启用时返回完整插件 hook，插件禁用时成功返回空 hooks 清单。单凭空清单不能证明没有配置；Q9 已确认接受并明确提示这一范围。
- 上述枚举实验只调用 `initialize`、`initialized` 与 `hooks/list`，没有启动 thread／turn 或执行 hooks，没有修改真实用户配置。
- 写入补验通过：以清单返回的完整 key 定位 `hooks.state."<key>".enabled`，通过 `config/value/write`、`mergeStrategy: replace` 和当前用户配置层的 `expectedVersion` 保存后，清单反映新的启用状态；重启 app-server 后仍保持。
- 已信任 fixture 的 `trusted_hash` 与信任状态在启停后保持不变；未信任 fixture 在启停后仍未信任，也没有新增 `trusted_hash`。这验证了启用与信任独立；产品仍按 Q4 限制，只启停已信任的 hooks。
- 相邻 hook 状态、其他配置字段和注释均保留。外部修改配置后，旧 `expectedVersion` 写入被 `configVersionConflict` 拒绝，未覆盖外部修改。
- `expectedVersion` 仅保护目标用户配置文件，不保护独立 hook 定义文件或插件内容；保存前仍需重新核实 `key` 与 `currentHash`，不宣称跨文件事务。
- 实现阶段补验覆盖已信任的用户与插件 hook：逐条禁用、重新启用后重启 app-server 读取，信任记录、无关配置、注释及定义文件均保留。禁用插件的清单过滤、总开关关闭和旧配置版本拒绝也已验证。全部测试只操作独立临时 fixture，未执行 hooks、未验证运行中会话即时生效，也不构成所有来源层组合或跨版本保证。

## 接入边界

- 读取使用 Codex 原生 `hooks/list`，沿用当前环境解析出的 Codex home，优先 `CODEX_HOME`，否则 `~/.codex`；显示实际目录，不新增多 home 切换。查询使用项目外工作目录，过滤用户与插件来源，避免把当前项目配置带入清单。
- 展示清单返回的 hook 启用状态与信任状态，不把它们描述为用户显式配置值或会话运行状态。托管、来源无法确认、待信任或定义已修改的条目不提供启停，并说明原因。
- 保留原生 `key`、`currentHash` 和来源信息；同事件、同命令但来自不同定义的条目不自行合并。来源警告与读取错误应可见，无法核实的清单不能宣称完整。
- hooks 总开关状态通过当前范围的原生 `experimentalFeature/list` 核实，用户配置版本与字段归属通过 `config/read` 核实。关闭时明确说明其阻止清单枚举；无法核实时说明未知。已禁用插件的 hooks 不展开，提供范围提示及「已安装插件」入口。
- 保存交由官方通用配置写接口，只修改当前用户配置内目标 key 的 `enabled`。完整 key 按一个 TOML 字符串键引用，不按其中的点、冒号或路径拆分；不生成自己的身份或 hash，不修改 `trusted_hash`、定义内容、项目设置、全局开关或插件启用设置。
- 保存前重核同一 home、目标身份、定义 hash、信任与启用状态及可维护资格；用户配置无法读取或解析时不写入。使用确认时的用户配置层版本防止覆盖外部变更；发生冲突后重新读取，由用户重新选择和确认，不自动覆盖重试。
- 原生清单读取、配置保存与保存后读取分别处理成功或失败。配置已保存但刷新失败时如实报告，并将旧数据标记过期，不能引导用户误以为保存未发生。

## 页面与操作流程

1. 侧栏「Codex」内提供「已安装插件／市场源／Hooks」页签，保留既有插件与市场管理能力。
2. 进入 Hooks 时展示当前 home、管理范围、CLI 能力与总开关状态，再呈现可核实的清单、警告或限制。
3. 列表提供已确认字段，详情展示完整配置内容；待信任或定义已修改时引导用户在 Codex 原生界面审查。
4. 用户对一条已信任且可维护的 hook 选择启用或禁用，确认事件、操作摘要、来源、目标状态及配置保存的含义。
5. 保存前执行身份与状态复核；取消、目标变化或无法核实时不执行旧操作。
6. 保存后重读并分别呈现两个阶段的结果；提示在新会话中验证，允许用户手动刷新以观察外部修改。

## 验收场景

| 场景 | 预期行为 |
| --- | --- |
| CLI 缺失或缺少所需能力 | 说明具体原因，不伪装为空清单 |
| hooks 总开关关闭 | 显示已关闭及无法枚举的原因，不宣称没有配置，不提供总开关操作 |
| 插件已禁用 | 不自行扫描其 hooks，清楚说明覆盖限制并提供插件管理入口 |
| 用户 JSON 与 TOML 均包含 hooks | 按原生结果展示两个来源并呈现警告，不自行选择覆盖优先级或去重 |
| 同一事件或命令有多条定义 | 保留各自身份、来源和状态，操作准确指向选中的一条 |
| 清单包含待信任或定义已修改的 hook | 显示对应状态并引导原生审查，不在本工具授予信任或启停 |
| 条目由策略管理或来源无法确认 | 只读并显示原因，不绕过限制 |
| 正常启停已信任的用户或插件 hook | 只保存该 key 的用户级启用覆盖，保留信任记录、定义及其他配置 |
| 用户取消确认 | 不写入配置 |
| 确认后定义、信任、状态、home 或资格变化 | 中止旧操作，刷新后由用户重新选择或确认 |
| 确认后用户配置被外部修改 | 版本检查拒绝旧写入，保留外部变更，不自动覆盖重试 |
| 定义文件与用户配置分别被修改 | 分别执行定义复核与配置版本检查，不宣称存在跨文件原子保证 |
| 配置无法读取、无法解析或保存失败 | 说明原因，不覆盖无法理解的配置，不仅凭点击翻转状态 |
| 保存成功但随后清单刷新失败 | 分别报告保存成功与读取失败，将旧清单标为过期 |
| CLI 与 App 使用不同 home 或已有会话未重载 | 只承诺页面展示范围内的配置保存，不宣称另一环境或运行中会话已生效 |
