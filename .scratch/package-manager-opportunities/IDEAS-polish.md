# Package Manager Control Center：打磨已有功能创意

## 工作假设

- **产品：** macOS 优先的本机开发环境观察与维护工具，界面由 Tauri 2 承载。
- **目标用户：** 使用多个包管理器、本地项目、VS Code 和编程代理工具的个人开发者；按 [PRODUCT.md](../../PRODUCT.md) 的确认结果，受众可扩展到更广泛的 macOS 开发者。
- **本轮目标：** 不新增管理器、清理能力或维护入口，打磨现有“先观察、再行动”的深度、清晰度、速度和可信度。
- **期望结果：** 用户更快理解“观察到了什么、哪些还不完整”，更少误判空白与失败，更少在扫描和页面切换中丢失上下文，并在操作后更容易确认实际发生了什么。
- **本轮边界：** 不引入后台自动刷新、跨管理器批量维护、派生数据清理撤销，也不重复已完成或进行中的专项工作。`操作资格说明` 仍在进行中；下列创意补充它，而不是替代它。
- **判断基础：** README、PRODUCT.md、现有 PRD、`src/` 与 `src-tauri/src/` 中的实际状态模型和页面结构。没有真实用户研究数据，以下优先级是待验证假设。

## 机会判断

产品已经不缺观察面：12 个管理器、25 个观察项、9 个顶层入口，覆盖包、运行时、缓存、项目派生数据、编辑器存储和代理扩展。下一阶段的主要摩擦不再是“能不能看到”，而是：

1. **同一事实有多种表达。** `ObservationCoveragePage` 已建立一套观察状态词汇，但管理器页、会话页、VS Code 页和代理扩展页仍各自组织状态、时间和下一步。
2. **操作结果与发生现场分离。** 维护历史保存了完整的执行与核对结果，但来源页主要显示进行中的操作；用户要回答“刚才到底清掉了什么”仍需要跳到历史页。
3. **等待过程不透明。** 扫描已有 `queued / reading / enriching` 阶段，但缺少已用时间、当前步骤和取消入口；项目扫描已有停止能力，管理器扫描没有。
4. **页面切换会丢失工作现场。** 顶层页面按条件渲染，搜索、筛选、排序、展开状态和滚动位置属于页面本地状态，离开即重置。
5. **“旧”与“变”没有被区分。** 观察覆盖度能说明上次观察时间，但在没有后台刷新的前提下，用户无法低成本知道当前范围“可能已经变化”。

这些摩擦都落在已有功能内部，适合用打磨而非扩张来解决。

## 分视角创意

### 产品经理

1. **维护结果就地闭环**
   在每个来源页保留最近一次维护的冻结范围、执行结果、核对结果和可测得的变化，直到下一次观察，并提供回看历史详情的入口。
   价值：让用户在操作现场直接确认结果，不必把“记得去历史页”当作流程的一部分。

2. **首轮能力盘点引导**
   首次进入或打开设置时，只读检测各管理器 CLI／配置目录是否存在，展示“已发现／未发现／无法判断”，并建议一组可启用的管理器；不扫描内容、不安装任何东西。
   价值：新用户能理解为什么有些页面是空的，也避免一次启用 12 个管理器后面对长时间扫描。

3. **维护后的验证清单**
   在操作结果旁按领域给出“如何在应用外验证”的可复制步骤，例如新会话中检查代理设置、确认 VS Code 已退出、区分目录占用与立即释放的磁盘空间。
   价值：产品无法观察所有生效结果，明确验证路径能减少“看起来成功了但不确定”的焦虑。

4. **页面级观察范围摘要**
   在每个来源页标题区用一句话说明本次读取覆盖了什么、哪些路径或清单未读取、上次成功观察是什么时候，而不是只显示条目数量。
   价值：把“零条”和“未读取”分开，让页内决策不依赖用户先记住观察覆盖度页。

5. **可携带的隐私安全观察报告**
   从现有观察生成一份可复制的摘要，包含管理器与版本、关键路径、观察完整度、失败命令和范围说明，默认隐藏用户名与令牌等敏感信息。
   价值：面向更广受众时，支持排查和跨机器对比的成本更低；不新增维护能力，只复用已有观察。

### 产品设计师

1. **统一观察状态组件**
   用同一套“状态徽章 + 观察时间 + 完整性 + 一个下一步”组件替换各页面临时组合的文案与颜色。
   价值：用户不必为 12 个管理器分别学习“空、未扫描、部分、失败、不可用”的视觉语言。

2. **统一确认影响摘要**
   所有确认面板顶部使用同一种影响摘要：将处理多少目标、哪些目标不可恢复、预计或已测得多少空间、哪些后续读取尚未完成；领域细节放在摘要之下。
   价值：确认框的第一眼回答“我会失去什么”，安全边界不因页面不同而改变。

3. **跨页上下文保持**
   在一次会话内保留每个页面的搜索、筛选、排序、展开项、滚动位置、选中对象和返回焦点；重新观察后对选中对象做身份校验，并提供显式重置。
   价值：总览 → 管理器 → 历史 → 项目清理是高频往返路径，反复重建筛选是最容易被感知的粗糙感。

4. **长列表可读性**
   为包、Maven 版本、会话记录、插件目录和历史记录统一粘性表头、路径截断与复制、关键列优先级、键盘行操作和窄窗口折叠。
   价值：真实环境常有数百到数千条目，横向滚动和丢失列上下文会直接降低观察效率。

5. **错误恢复文案模板**
   统一为“发生了什么 + 依据是什么 + 现在能做什么”，把原始 stderr 收进可复制的详情；执行失败与后续读取失败继续分开表达。
   价值：现有诊断信息很丰富，但呈现方式随领域变化，用户需要重新判断哪些是故障、哪些只是未读取。

### 软件工程师

1. **可取消的管理器扫描与阶段进度**
   在现有 `queued / reading / enriching` 之上增加已用时间、当前管理器、阶段内进度，并提供“当前步骤完成后停止”；取消后保留已完成结果并标记范围。
   价值：项目扫描已有停止能力，管理器扫描仍只有“扫描中”；透明度和可控性可以显著降低等待焦虑。

2. **廉价变化指纹**
   为扫描根目录、管理器缓存路径和代理配置目录计算低成本的 mtime／size／计数指纹；页面重新进入或用户主动检查时提示“可能已变化”，一键重新观察，不启动后台定时器。
   价值：在不违反“无自动刷新”约束的前提下，避免把旧观察当成当前事实。

3. **操作前差异预览**
   确认时对冻结目标与当前状态做确定性差异：新增、消失、身份变化、大小变化；有实质变化时要求重新确认，而不是只用一句“目标已变化”中止。
   价值：把安全检查从“被阻止”变成“看得懂的阻止”，也补足操作资格说明只回答能不能做、不回答变了什么。

4. **大列表虚拟化与性能预算**
   对包、会话、Maven artifact 和历史列表做虚拟化或窗口化渲染；记录原生命令耗时与扫描阶段耗时，为慢路径提供可诊断信息。
   价值：受众扩大后，环境规模和列表长度都会上升；性能问题通常先在渲染而不是扫描上暴露。

5. **跨边界契约与类型生成**
   从 Rust 边界类型生成或校验 TypeScript 类型，并用 golden fixtures 固定关键 JSON 形状；统一成功、部分、失败和不可用的结果外壳。
   价值：12 个管理器适配器和 25 个观察项让手写类型漂移的代价变高，契约测试能把问题挡在界面之前。

评级相对于“打磨现有观察与维护闭环”这一目标：高、中、低。可行性表示交付一个可验证首版有多容易，因此“高”代表更容易验证与实现。

### 1. 统一观察状态组件

用同一套“状态徽章 + 观察时间 + 完整性 + 一个下一步”组件贯穿管理器、VS Code、会话、Codex／Claude 和项目清理页。

**入选原因：** 观察覆盖度页已经定义了 25 个观察项的状态语义，但来源页仍各自表达。用户最常犯的错误不是不会操作，而是把“未读取”当成“没有内容”，或把“部分读取”当成完整结果。统一组件可以直接复用现有状态模型，改动面广但风险低。

**关键假设：**

- 用户确实会把空白列表、零条目和未扫描混为一谈。
- 一套共享组件能保留各领域的差异，例如“目录不存在”是已观察事实，而“CLI 缺失”是不可用。
- “下一步”只包含查看、刷新、调整范围等现有动作，不引入自动修复。

**最小验证：** 用合成状态在管理器页和 VS Code 页做高保真原型，让开发者完成“现在是否适合执行维护”的判断，比较正确率与用时；不执行任何维护。

**首批落点：** `managerScanning.ts` 的状态标签、`ObservationCoveragePage` 的词汇、各来源页标题区与空状态。

### 2. 维护结果就地闭环

在每个来源页保留最近一次维护的范围、执行结果、核对结果和可测得的变化，直到下一次观察，并链接到历史详情。

**入选原因：** 维护历史已经能保存冻结目标、逐项结果与后续读取，但来源页只负责进行中的操作；用户完成清理或卸载后，要确认“发生了什么”仍需离开当前任务。把已有历史投影回来源页，不需要新的持久化模型，却能显著增强操作后的信任。

**关键假设：**

- 用户操作后会回到来源页继续观察，而不总是直接去历史页。
- 带时间戳的旧结果不会被误认为当前状态。
- 可测得的变化可能不存在；此时应显示“未测量”，而不是 0 或估算值。

**最小验证：** 记录操作后来源页与历史页的实际跳转路径，或用原型测试用户能否在不离开来源页的情况下回答“清理了多少、核对是否成功”。

**首批落点：** `maintenanceHistory.ts` 的记录摘要、管理器页、项目清理页、VS Code 页和会话页。

### 3. 可取消的管理器扫描与阶段进度

把现有的排队、读取、补充测量阶段扩展为带已用时间、当前步骤和“完成当前步骤后停止”的扫描过程，取消后保留已完成结果并明确标记范围。

**入选原因：** 项目清理已经提供扫描停止入口，管理器扫描仍只显示“扫描中”。12 个管理器加上补充测量可能持续较久，用户无法区分“正在工作”和“卡住了”。扫描是只读的，取消风险远低于维护操作，适合先做。

**关键假设：**

- 取消只影响读取与测量，不会留下需要清理的中间状态。
- 部分结果对用户有价值，只要明确标记“已停止／不完整”。
- 阶段内进度可以达到足够可信的粒度，不需要伪造百分比。

**最小验证：** 在大型 pnpm store 或多个扫描根目录上测量扫描时长与放弃率；先为管理器扫描加取消按钮和已用时间，观察是否减少重复点击刷新。

**首批落点：** `usePackageManagers.ts`、管理器扫描队列、`ManagerTabs` 和总览扫描按钮。

### 4. 跨页上下文保持

在一次会话内保留每个页面的搜索、筛选、排序、展开项、滚动位置、选中对象和返回焦点，并在重新观察后校验选中对象是否仍然存在。

**入选原因：** 顶层页面按条件渲染，本地状态随卸载重置。真实使用路径经常是总览发现问题 → 进入管理器筛选 → 查看历史 → 回到项目清理，反复重建筛选是低成本、高感知的粗糙点。它不改变任何安全边界，适合作为快速见效的打磨。

**关键假设：**

- 用户把跨页往返视为同一项任务，期望上下文延续。
- 恢复旧选择不会造成误操作，只要在执行前重新校验身份。
- 用户需要显式的“清除筛选／重置视图”，而不是依赖离开页面来重置。

**最小验证：** 在两个页面（例如会话记录和项目清理）实现会话级状态保持，观察返回后继续任务的时间是否下降；同时验证选中对象消失时的降级提示。

**首批落点：** `SessionRecordsPage`、`VscodeStoragePage`、`ProjectCleanupPage`、`ManagerTabs` 的本地状态。

### 5. 廉价变化指纹与“建议重新观察”

为已观察范围计算低成本的文件系统指纹，在页面重新进入或用户主动检查时提示“可能已变化”，并提供一键重新观察，不引入后台自动刷新。

**入选原因：** “不做后台自动刷新”是明确的产品边界，但用户仍需要知道当前观察是否可能过期。观察覆盖度能显示上次观察时间，却不能说明范围是否变化。mtime／size／计数指纹比完整扫描便宜得多，可以把“新鲜度”变成可行动的提示，而不是让用户凭时间猜。

**关键假设：**

- 对目标目录和配置文件做轻量元数据检查足够快，不会让页面进入变慢。
- 指纹变化会有误报；文案必须使用“可能已变化”，并允许用户忽略。
- 检查只读元数据，不读取包清单、会话正文或配置内容。

**最小验证：** 在大型 pnpm store、Homebrew cache 和一个项目根目录上测量指纹耗时；用原型验证用户看到提示后是选择重新观察、忽略还是离开。

**首批落点：** 管理器范围、项目扫描根目录、VS Code 存储目录、Codex／Claude 配置目录；对应现有观察项 ID。

## 值得进入下一轮

- 首轮能力盘点引导：适合在受众扩大和分发方式确定后优先验证。
- 统一确认影响摘要：与操作资格说明互补，适合在资格文案收口后统一视觉。
- 操作前差异预览：安全价值高，但需要逐领域定义稳定身份和实质变化阈值。
- 大列表虚拟化与性能预算：在真实大环境样本出现后再投入，避免过早优化。
- 跨边界契约与类型生成：工程杠杆高，但用户不可见，适合作为持续重构而非单独立项。
- 维护后验证清单、错误恢复文案模板、长列表可读性、隐私安全观察报告：可分别作为小型打磨批次。

## 建议的首个实验

在管理器页和 VS Code 页用合成状态制作“统一观察状态组件 + 最近维护结果条”的原型。请几位使用多个包管理器的开发者完成两个任务：

1. 判断当前是否可以执行维护，以及还缺什么证据；
2. 在不进入历史页的情况下说明上一次维护实际发生了什么。

衡量判断正确率、任务用时和口头困惑点。原型只读取 fixture，不执行扫描或维护。这个实验同时验证前两个优先级，成本低，且不会触碰维护安全边界。

## 待确认

- 目标用户是否仍以“多管理器个人开发者”为主，还是优先面向首次使用者？这会改变首轮引导的优先级。
- 成功指标更偏向“减少误操作”“减少等待”还是“减少理解成本”？三者会得到不同的前五排序。
- 是否接受为“变化指纹”增加一个只读的轻量原生命令；如果坚持零新增命令，第 5 项应替换为“统一确认影响摘要”。
